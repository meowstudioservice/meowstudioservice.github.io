# /release_app

사용자가 `/release_app` 또는 `$release-app`을 명시적으로 호출했을 때만 실행한다. 스킬 설치·수정·설명 요청은 릴리즈 실행이 아니다. 스킬이 없거나 호출되지 않으면 테스트 빌드이며 버전·빌드 번호를 유지한다. 이 스킬의 호출은 대상 앱의 main 병합, 태그, 비공개 테스트 업로드, 출시노트 작성과 검토 요청을 포함한다. 프로덕션 승격은 포함하지 않는다.

## 준비

1. 대상 저장소의 AGENTS.md와 빌드 문서를 읽고 앱·패키지·원격·버전 원본·서명·기존 비공개 테스트 트랙을 확인한다. 여러 앱이면 요청으로 특정된 앱만 처리한다. 웹사이트·문서 전용 저장소에는 Android 버전이나 Play 배포를 만들어 넣지 않는다.
2. 기존 미커밋 작업을 보존하고 이번 릴리즈에 포함할 변경만 식별한다. 저장소의 이슈·브랜치 규칙을 지킨다. 인증·서명·트랙 접근을 먼저 확인한다. 필요한 권한이 없으면 준비 가능한 부분을 끝내고 정확히 어떤 단계가 막혔는지 보고한다. 실패를 이유로 다른 트랙에 제출하지 않는다.
3. Google Play Console 또는 연결된 Developer API에서 **실제로 사용자에게 출시된 가장 최신 Production 릴리즈**를 확인한다. 로컬 최신 버전, 직전 테스트 업로드, GitHub Release, 가장 최근 태그를 Production이라고 추정하지 않는다. 자세한 기준은 [production-baseline.md](references/production-baseline.md)를 따른다.

## 버전과 출시노트

4. 앱 표시 버전과 빌드 번호를 모두 증가시킨다. 버전 원본과 빌드 시 재설정하는 파일을 함께 맞춘다. 표시 버전은 main·현재 작업 버전보다 높게, 빌드 번호는 main·현재 작업 및 Play 전체 트랙/사용된 업로드 번호보다 높게 정한다. 숫자가 충돌하면 배포 이력을 확인하고 새 번호를 사용한다. 과거 특정 릴리즈의 예외를 새 릴리즈에 재사용하지 않는다.
5. Production 버전과 대응하는 Git 커밋을 검증하고, 그 커밋 이후 이번 릴리즈 후보까지의 **누적 변경**으로 출시노트를 작성한다. 중간 비공개 테스트에 포함되었어도 아직 Production에 없는 변경은 포함한다. 되돌린 변경, 미포함 기능, 내부 커밋 목록을 그대로 사용자용 노트에 넣지 않는다. 기존 지원 언어별로 작성하고 Play 입력 제한을 확인한다.
6. 변경 범위와 저장소 지침에 맞는 검사·빌드 검증을 수행한다. 확인한 Production 버전/코드/커밋/조회 시각/출처, 대상 버전, 변경 범위, 출시노트, 검사 결과를 산출물 폴더에 기록한다. 비밀값은 기록하지 않는다.

## main 병합과 태그

7. 검사를 통과한 코드를 PR로 main에 **merge commit** 병합한다. 일반 변경은 버전을 유지하고 태그를 만들지 않는다. 릴리즈 PR 본문과 최종 병합 커밋 메시지에는 각각 독립된 줄로 아래 표시를 넣는다. 사용자가 스킬을 호출하지 않았는데 표시만 추가해서 검사에 통과시키지 않는다.

   ```text
   Release-Skill: release_app
   ```

   PR 본문에는 실제 연결 이슈, Production 기준 버전·커밋과 조회 근거, 출시노트, 검사 결과도 포함한다. `gh pr merge --merge --body-file <파일>` 등으로 병합 메시지에도 표시를 보존한다. main이 바뀌면 최신 main을 통합하고 버전 비교·필요 검사를 다시 수행한다. squash/rebase merge, 강제 푸시, 무관한 작업 포함은 하지 않는다.
8. 정확한 main 병합 커밋에 annotated tag `v<버전>+<빌드번호>`를 생성한다(예: `v1.2.3+45`). 기존 Tag release CI가 있으면 완료와 원격 태그 대상을 확인한다. 없으면 스킬이 같은 형식의 주석 태그를 생성하고 푸시한다. 기존 태그는 이동·덮어쓰지 않는다.
9. 태그가 가리키는 깨끗한 소스에서 최종 서명 AAB를 빌드하고 패키지·버전·빌드 번호·서명·SHA-256을 확인한다. 기존 문서가 정한 산출물 경로를 사용한다. 사전 빌드를 재사용하려면 태그 소스와 실제 입력이 동일함을 증명한다. 무관한 미커밋 코드가 있는 작업 트리에서 최종 업로드 파일을 만들지 않는다.

## Google Play 비공개 테스트 제출

10. 업로드 직전에 Production 기준이 달라졌는지 다시 확인한다. 달라졌으면 새로운 Production 이후 변경으로 출시노트를 갱신한다.
11. 실제 **Closed testing(비공개 테스트)** 트랙에 검증된 AAB와 언어별 출시노트를 올린다. Internal testing, Open testing, Production은 대체 경로가 아니다. 트랙 이름만 보고 종류를 추측하지 않는다. 기존 테스터·국가 설정을 보존한다.
12. 릴리즈 저장에서 끝내지 말고 게시 개요에서 해당 변경의 **검토 요청 제출**을 완료한다. API 업로드나 edit commit 성공만으로 심사 접수를 단정하지 않는다. Console 상태 또는 명시적인 제출 결과를 확인한다. 초안·미전송 변경만 남아 있으면 미완료로 보고한다. 검토를 자동 요청할 수 없는 API/앱 상태라면 Console로 마무리한다. 무관한 대기 변경이 함께 제출되는지 확인한다.
13. 완료 보고에는 버전+빌드, main 병합 SHA, 원격 태그, AAB·체크섬, Production 기준, 출시노트, 비공개 테스트 트랙, 검토 접수 근거를 포함한다. 제출 완료와 Google 심사 승인을 구분한다. 중간 실패 시 성공 단계와 재개 지점을 남기고 같은 버전으로 새 바이너리를 무작정 재업로드하거나 새 버전을 자동 연속 생성하지 않는다.

## 이후 프로덕션

프로덕션은 별도 출시 요청이 있고 비공개 테스트의 승인·배포·실제 테스트 완료 근거가 있을 때만 진행한다. 비공개 테스트를 통과한 **동일한 AAB/versionCode**를 승격하며, 승격만을 위해 재빌드하거나 번호를 올리지 않는다. 수정이 필요하면 새 `/release_app` 릴리즈로 다시 비공개 테스트부터 시작한다. 승격 시에도 최신 실제 Production 이후의 출시노트를 확인한다.
